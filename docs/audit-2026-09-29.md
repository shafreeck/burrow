# 2026-09-29：证书、agent、协议和系统代理审计

## 结论

`--tunnel --domain` 现在使用已有固定 Cloudflare 隧道，保留本机 HTTP，
不会触发 ACME 或启动随机隧道。公网直接部署用 `--acme --domain` 或
`--tls-cert/--tls-key`。HTTP-01 验证服务必须先于签发启动。

代理入站默认全部关闭。通过可重复的 `--bind 协议://主机:端口` 显式指定，
支持 HTTP、SOCKS5、VLESS、Trojan，也支持同一协议的多个监听地址。
控制面由 `--listen` 指定，默认 `127.0.0.1:9000`。
`--system-proxy` 使用第一条 `http://` 绑定，支持内网/公网地址；通配监听地址
转换为本机回环地址。它只设置运行 server 的机器，VPS 的远程客户端需单独配置。

agent 与 VLESS/Trojan 的 TCP 主路径已有本地端到端验证，但实现范围仍然有限，
不能描述为完整的 Xray 或 Trojan 服务端替代品。

## 本次修复

| 问题 | 原行为 | 修复与证据 |
|---|---|---|
| 固定 Tunnel 误触发 ACME | `--tunnel --domain` 在监听前申请证书，验证失败 | 模式明确分支；独立进程测试确认提供 HTTP、没有 ACME 或 cloudflared 子进程 |
| ACME 验证服务未运行 | 注册了 handler，却没有监听端口 | 签发前绑定 `--acme-listen`；本地 CA 真正请求挑战 URL，成功和失败后都回收 token、释放端口 |
| ACME 掩盖失败 | 丢弃 challenge error；授权一直 pending 仍继续 finalize | 返回 CA 原始 detail/type；轮询耗尽立即失败；测试确认未调用 finalize |
| ACME JWK 坐标编码 | 省略 P-256 坐标的前导零，偶发生成不合规 JWK | 固定为 32 字节；测试使用有前导零的真实曲线点 |
| agent 上游代理 | 忽略用户名/密码、HTTPS scheme；握手可能长时间卡住 | CONNECT Basic 认证、HTTPS 代理 TLS 校验、上下文取消和握手期限；测试认证与同包到达的数据 |
| agent 会话清理 | 断线后仍在进行的拨号可能留下连接 | 每个 WebSocket 会话单独管理流，取消待连接请求，拒绝迟到连接；关闭期间真实 CONNECT 的测试 |
| agent 认证及重连 | 未确认 hello_ack 即处理消息，退避可能变成 32 秒 | 必须收到成功确认；最大退避 30 秒 |
| 网络切换后半开连接 | TCP 没有报错时一直阻塞 ReadFrame，无法进入重连循环 | 协商应用层 ping/pong，10 秒发送、20 秒超时；测试先复现不重连，再验证断线后新的真实 HTTP 请求成功；旧 server 降级为 WS ping |
| server 残留 agent | 旧连接和阻塞的流队列可能使失联 agent 留在可选列表 | 协商心跳的 agent 45 秒无心跳即独立执行清理；测试覆盖阻塞流和 pending 请求回收；旧 agent 不启用该期限 |
| TUN 隧道恢复 | 只按域名识别 Cloudflare，数字 IP 漏掉；MUX 等待 agent 后才判断绕行 | 识别官方 Global/US 具体 IPv4/IPv6 的 7844 端口与 cftunnel.com；5 类入站在没有 agent 时用真实本地 TCP 测试绕行（外部拨号替换为本地目标） |
| MUX 跨 agent 重连 | MUX 连接一直持有初次连接的 agent | 新逻辑流选择当前 agent；同一个 MUX 连接在 agent 断开、重连后继续完成 echo 的测试 |
| 出口 CA 变化 | 安装器写死历史 CA，文档承诺只装一次 | 支持 `--install-ca --ca-cert`；拒绝非 CA、过期 CA 和多证书文件；安装前显示指纹；文档要求从当前 VM 信任库导出和核对 |
| 多 agent 隔离 | 一个 agent 的断线清理会失败所有 pending；close/result 未验证所属 agent | 请求带 owner，只接受对应 agent 的完成和关闭消息 |
| TCP 首尾数据 | CONNECT 成功后才注册流；done 与数据同时就绪时随机丢尾包 | 发请求前注册，关闭后排空已收到的数据；VLESS/Trojan/HTTP CONNECT/SOCKS5 真实 agent 转发测试 |
| VLESS MUX 握手 | 读 command 时额外消耗首帧 3 个字节 | MUX 只读取 command；测试验证紧随其后的帧完整保留 |
| MUX 首帧与会话复用 | 首帧 data 缺少 type；直连首帧发错出口；结束后 session ID 留在映射中 | 首帧按对应连接转发；会话结束后回收；真实 TCP echo 和同一 ID 重用测试 |
| VLESS TLS | 设置证书后 VLESS 仍监听明文 TCP | VLESS/Trojan 使用共同的 TLS listener；测试校验 TLS 证书并转发 TCP 数据 |
| VLESS UDP 控制流 | Cloudflare 域名的 UDP 可能走进 TCP bypass 分支 | TCP bypass 仅匹配 TCP；UDP 使用带物理接口绑定的直接拨号（Windows 使用 OS 路由） |
| 协议校验 | 空域名、零端口、非空 VLESS flow/addon 被接受；MUX 长度可能截断 | 明确拒绝不支持或不合法的请求/长度；Trojan 使用标准恒定时间比较 |
| WebSocket 稳定性 | 64 位帧长转 int 可溢出并 panic；并发 Close 可重复关闭 channel | 转换前检查无符号长度；Close 使用 sync.Once；写入有长度和超时限制 |
| HTTP fetch 资源 | 8 MiB 经过 base64 会超过帧限制，且可能静默截断；传输连接未回收 | body 上限 4 MiB，超限返回错误；会话取消传递给请求并回收空闲连接 |
| 平台构建 | Windows 缺少接口绑定实现；Linux 对短接口名可能越界 | Windows 构建补齐，Linux/macOS 用前缀判断；macOS 区分 IPv4/IPv6 socket option |

## 系统代理参数

`--system-proxy` 等待 HTTP 代理绑定成功、首个 agent 完成认证后才切换桌面设置。
默认不开启。修改前创建用户配置目录下的 `burrow/system-proxy.json` 快照；
设置失败回滚；Ctrl-C/SIGTERM/运行错误退出时恢复；强制终止或断电后运行
`--restore-system-proxy`。已有快照时拒绝再次覆盖。

恢复前读取当前设置，只恢复仍属于本次运行的值；其他应用的改动会保留，
并留下快照和错误供后续处理。

| 后端 | 实现 | 验证范围 |
|---|---|---|
| Windows | WinINet per-connection API；包括手动代理、PAC URL、自动检测标志和 bypass | Windows amd64 构建及 vet；原生 API 实机读写待验证 |
| macOS | networksetup；HTTP/HTTPS、PAC 和自动检测；可指定网络服务 | 真实配置只读核对；命令后端的设置/恢复模拟测试；未修改本机现有代理 |
| GNOME | 当前会话的 GSettings；检查配置是否可写 | 模拟后端设置/恢复测试、Linux amd64 构建；原生桌面待验证 |
| KDE 5/6 | kreadconfig/kwriteconfig 管理 kioslaverc；D-Bus 刷新 | 模拟后端设置/恢复测试、Linux amd64 构建；原生桌面待验证 |

设置只影响遵循桌面代理配置的应用，不改变 Windows WinHTTP 服务代理、
当前 shell 环境变量或 TUN 路由。无桌面 Linux 明确报错。macOS 已有认证代理
时拒绝覆盖，因为 networksetup 不提供可用于恢复的密码。

## 剩余限制

1. **VLESS UDP 出口是 server 本机。** agent 协议仍只有 TCP 流，不能把 UDP 描述成 VM 出口。MUX UDP/XUDP 未实现。
2. **Trojan 只实现 TCP 子集。** UDP ASSOCIATE、伪装回落和探测伪装未实现；本机明文模式不具备标准公网 Trojan 的 TLS 行为。
3. **没有 TCP 半关闭。** 一侧 EOF 会关闭整条逻辑流，依赖 `CloseWrite` 后继续读响应的协议仍可能受影响。
4. **MUX 新连接与共享 WebSocket 有阻塞传播。** 新目标拨号会阻塞该 MUX 连接的读取；慢流的写入/队列背压会影响其他流。尚未实现独立调度与公平队列。
5. **HTTP fetch 是受限缓冲路径。** 4 MiB body 上限；多值响应头（例如多条 Set-Cookie）仍只保留一个值；不提供完整流式 HTTP 代理语义。
6. **ACME 是启动时签发。** 尚无证书缓存复用、持久账户、运行中自动续期或完整 badNonce/Retry-After 重试策略。长期服务建议用外部证书管理。
7. **未完成第三方客户端矩阵。** 本地测试使用协议字节和真实 agent；尚未用各版本 Xray、sing-box、Shadowrocket 做全面互操作测试。Vision、REALITY、非空 flow/addon 不支持。
8. **WebSocket 是内部协议子集。** 已有协商式应用层心跳；无分片支持或完整 RFC 6455 负向校验矩阵。旧 server 的 WS ping 回退只能检测传输存活，不能保证反向代理后方应用可达。
9. **Windows TUN 绕行需用户路由配置。** 系统代理使用 WinINet，但物理接口绑定未实现；cloudflared 需要由 TUN 客户端排除。

## 本机入口与公网验证

初次检查时，本机 `127.0.0.1:9000` 返回 200，公网返回 502。
已有 cloudflared 的 `/ready` 返回 200，但 `/config` 版本为 -1，只有默认规则。
用户重新添加发布规则后，连接器收到版本 1：
`burrow.lyra.run → http://localhost:9000`。公网 HTTP/1.1 和 HTTP/2 HTTPS GET
均返回 200 及 `burrow server. Agent: /ws`。

使用重新编译的 agent 经 `wss://burrow.lyra.run/ws` 成功建立连接并完成
hello/hello_ack。通过 server 的 HTTP CONNECT 和 SOCKS5 请求
`https://example.com/` 均返回 200、713 字节，TLS 校验成功。
测试 agent 在本机运行，上游是本机已有的 `127.0.0.1:2080` 代理，
因此这证明了公网 Tunnel 和代理链路，不代表已验证 VM 出口。
临时测试 agent 已退出。验证后留下的 server 在用户手动启动时造成端口冲突，
随后已停止，并确认 9000、18080、8443、1080 端口释放，由用户手动启动。

本机 `8080` 已被 Morphz 使用，上述实测将 HTTP 代理指定为
`127.0.0.1:18080`；VLESS 为 `127.0.0.1:8443`，SOCKS5 为
`127.0.0.1:1080`。后续参数已统一为 `--bind`，各地址需要逐条显式指定。
未开启 `--system-proxy`；原生桌面配置没有被测试修改。

后续失联排查发现，回源 `localhost` 有时解析到 `[::1]:9000`，与 IPv4 监听不符；
cloudflared 记录了持续重试的 `/ws` 请求和 connection refused。
当前连接器配置版本 2 已改为 `http://127.0.0.1:9000`。
用户确认关闭 TUN 后 agent 能恢复。代码测试覆盖静默连接和绕行路径，
没有在用户的 TUN 配置中切换模式或验证所有客户端路由行为。

## 出口 CA 实测

经本机代理读取 `www.google.com` 的证书链，当前出口根 CA SHA-256 以
`A9:D6:3E:7B` 开头；排查时系统钥匙串与仓库内嵌 CA 都以 `21:D7:A6:51` 开头。
两者名称均为 `Hatch Sandbox Egress CA`，但密钥标识不同。
已安装根 CA 验证当前叶证书失败；同一链路返回的另一张根 CA 能验证该叶证书。
证书仍在有效期内，所以这次报错是签发链不匹配。
这只证明当前出口与历史 CA 不同，不能推出每次连接或每次 VM 启动都会更换。
未从当前 VM 信任库独立核对新根的来源，也未将捕获到的根 CA 加入系统信任。

随后用户提供 `hatch-egress-ca-latest.crt` 并要求替换内嵌证书。
该文件的自签名校验通过，指纹与上面当前出口的 CA 一致；已将其原样替换到
`internal/ca/hatch-egress-ca.crt`。此更新只改变程序内嵌证书，没有修改系统信任库。

## 检查结果

- `--bind` 回归覆盖：无代理绑定、单个 VLESS、多个协议、同协议多地址、IPv6 URL、非法参数和重复地址；缺少 HTTP 绑定时系统代理参数明确报错。
- 重编译后的独立进程经 `lsof` 核对：无绑定只监听 1 个控制面端口，单个 VLESS 监听 2 个端口，4 条代理绑定监听 5 个端口。所有测试进程均已正常退出并释放端口。
- 系统代理地址转换覆盖内网/公网 IP、IPv6、通配地址到回环地址；测试没有修改实际系统代理配置。
- `go test -race ./...`：通过，涵盖真实本地 agent/TCP/TLS 转发、ACME 挑战访问、会话隔离和代理恢复逻辑。
- `go vet ./...`、`git diff --check`：通过。
- Windows amd64、Linux amd64：server/agent 交叉编译及 `go vet ./...` 通过。
- macOS arm64：已重新编译工作区的 `burrow-server` 和 `burrow-agent`，并完成上述公网链路实测。
- Windows/Linux 原生桌面代理读写未在实机执行；模拟后端测试不能替代平台验收。
